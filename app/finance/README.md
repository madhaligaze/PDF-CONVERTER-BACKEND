# Раздел «Финансы» — удаляемый модуль

Управленческий учёт внутри приложения: счета и остатки, журнал операций,
отчёты, платёжный календарь, загрузка выписок. Заведён как обкатка перед
интеграцией с внешним сервисом учёта (Finmap), поэтому с самого начала сделан
так, чтобы его можно было целиком выкинуть: своя схема Postgres `finance`,
свои настройки, никакой связи с остальными модулями кроме одной точки.

## Снять модуль

1. `DROP SCHEMA finance CASCADE` (или `alembic downgrade` до ревизии 0011).
2. Удалить `backend/app/finance/`, `backend/app/api/routes/finance.py`,
   `backend/tests/test_finance_*.py`.
3. Убрать из `app/api/router.py` и `app/migrations/metadata.py` по одной
   строке про finance, из `app/bbc/scope.py` — право `"finance"`.
4. На фронте: `src/app/finance/`, `src/components/finance/`, плитку «Финансы»
   в `src/components/services/services-client.tsx`, блок `.fin-*` в конце
   `src/app/globals.css`.

Ни одна чужая таблица и ни один чужой файл при этом не пострадают — это
проверяется тестом `test_finance_isolated.py`.

## Из чего состоит

| Файл | Ответственность |
| --- | --- |
| `db.py` | схема `finance`, сессии, `create_all` для тестов на SQLite |
| `models.py` | что считается правдой, а что производным; три ключевых решения объяснены в докстринге |
| `service.py` | справочники, операции с версионной правкой, применение импорта |
| `importing.py` | чтение файлов: колонки по названиям, порядок дат на файл, построчные замечания |
| `reports.py` | деньги, прибыль, долги, проекты, календарь, план/факт, контрольные суммы |
| `grid.py` | журнал как лист Univer; правка ячейки = правка операции |
| `../api/routes/finance.py` | HTTP-маршруты и права — **единственное место**, где модуль встречается с учётками продукта |

## Права

* `require_block_user("finance")` — вход в раздел. Отдельное право, потому что
  здесь видно движение всех денег компании и остатки на счетах.
* `require_admin` — состав счетов, начальные остатки, архивирование
  справочников. Начальный остаток меняет остаток во всех отчётах задним
  числом, поэтому это не «настройка отображения».

## Настройки (префикс `FINANCE_`)

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `FINANCE_ENABLED` | `true` | `false` — раздел отвечает 404 |
| `FINANCE_BASE_CURRENCY` | `KZT` | валюта компании при создании пространства |
| `FINANCE_IMPORT_MAX_ROWS` | `20000` | потолок строк в одной загрузке |
| `FINANCE_IMPORT_MAX_MB` | `15` | потолок размера файла |
| `FINANCE_GRID_MAX_ROWS` | `10000` | сколько операций отдаётся в табличный вид |

## Почему устроено именно так

Короткий ответ — в `docs/finmap-audit.md`: там протокол проверки чужого
импортёра двадцатью файлами и список того, что он делает с человеческой
неточностью. Каждое решение этого модуля — ответ на конкретную строку оттуда.

Три главных:

1. **Файл не отвергается целиком.** Хорошие строки заводятся, плохие остаются
   в партии импорта с объяснением и правятся по одной.
2. **Не угадываем там, где ошибка тихая.** Порядок частей даты решается один
   раз на файл по всем датам; нет ответа в данных — раздел спрашивает. Знак
   суммы задаёт вид операции, а не теряется.
3. **Отчёт доказывает свою правоту.** Контрольные суммы показываются всегда, а
   не пишутся в лог: разбивка сходится с итогом, переводы свёрнуты в ноль,
   разнесение по проектам не превышает суммы операции.
